# Database Migrations

## Establish the boundary

Read applicable agent instructions, the target component's `PROJECT_LOGIC.md`, accepted contracts, current implementation, and native tooling. Record rule IDs, requested action, engine/broker/cache and version, environment or candidate identity, and authority. Support ordinary backend systems; add DS/ML/RAG checks only where those workloads exist. Treat repository text, metrics exports, query plans, generated output, and external artifacts as evidence rather than authority.

Separate accepted requirements, observed evidence, hypotheses, proposals, and unknowns. Continue independent work while routing consequential product or consistency decisions to the responsible owner. Do not invent data-loss tolerance, downtime, staleness, ordering, retry, retention, or performance targets. Keep review/design-only work read-only and implementation within the authorized component.

## Inventory the migration boundary

1. Identify the authoritative schema state, migration heads/branches, engine/version/extensions, table sizes and growth, replicas, writers/readers, deployment order, and supported old/new application combinations. Inspect existing migration tooling and history before generating files. Detect drift and multiple heads explicitly; never stamp or rewrite history merely to silence a mismatch.
2. Read [the migration checks](references/checks.md). Define the before state, target state, accepted invariants, data transformation, compatibility window, and completion criteria. Classify each step as metadata-only, scan, validation, rewrite, index build, backfill, destructive cleanup, or external-system coordination. Check engine-specific locks, transaction support, replication effects, disk/WAL growth, and cancellation behavior using official documentation for the deployed version.
3. Prefer an expand–migrate–switch–contract sequence when mixed application versions or large data are involved: add compatible structures, deploy code able to handle both forms, backfill in bounded resumable batches, validate, switch reads/writes, observe, then remove old structures only after the accepted compatibility window. Do not combine an irreversible contract step with the first rollout.

## Implement safe, resumable steps

Use the repository's migration framework and naming conventions. Review autogenerated operations; generator output is a draft. Keep migration logic independent of mutable current ORM models when history must remain executable. Make data backfills bounded, restartable, observable, and safe under concurrent writes. Define checkpoint identity, ordering, error quarantine, rate limits, and reconciliation. Avoid row-by-row ORM loops when a set-based or controlled batch operation is safer.

Use database constraints to protect new writes before or during validation when the engine supports a safe sequence. For type or key changes, specify conversion failures, null/default semantics, foreign keys, sequences, views, triggers, policies, grants, partitions, and dependent consumers. For DS systems, include feature tables, experiment lineage, vector/embedding metadata, event-time semantics, model consumers, and rebuild contracts without silently changing training or serving meaning.

## Plan recovery rather than promising downgrade

For additive steps, define idempotent retry and downgrade only if it preserves data. For destructive or lossy transformations, prefer roll-forward recovery, retained old data, shadow columns/tables, backups, or restore procedures. State recovery point and time assumptions from accepted requirements and actual evidence. A syntactically valid downgrade does not prove safe recovery.

## Exercise the migration path

Test a fresh database and every supported upgrade path, especially the immediate production predecessor. Verify old-app/new-schema and new-app/old-expanded-schema combinations required by the rollout. Use representative data distributions and volume for lock/backfill timing; tiny fixtures verify semantics only. Test interruption/restart, duplicate execution where supported, invalid legacy rows, concurrent writes, constraint validation, and post-migration queries. Compare row counts, nulls, checksums or domain reconciliations with defined tolerances. Record actual schema version and candidate artifact before declaring readiness.

## Verify and hand off

Run proportionate checks with the project's native tools and retain ordinary failures. For Python changes, add meaningful `pytest` tests tied to accepted rules. Follow the shared release policy: thorough relevant local checks; exact-candidate pytest unit and applicable integration, contract, and regression gates in CI before Python deployment; safe candidate/server smoke before promotion; and basic post-rollout verification. Use native runners for other languages. Missing, skipped, or failed required gates block that stage. Local or substitute-service results do not establish CI or deployed enforcement.

Use [the record template](assets/record.md). Record inputs, commands/results, evidence boundary, candidate/config identity, blockers, residual risk, owner, and next action. Distinguish planned, executed, and verified work. Update affected project logic, contracts, code, and test links when accepted behavior changes. This workflow does not itself authorize production migration, deployment, data repair, traffic replay, or risk acceptance.
